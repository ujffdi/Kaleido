## AndroidJunkCode 2.0.0

### Facts: public configuration

Configuration is variant-named: generation runs only when `variantConfig` contains an entry whose name exactly matches the AGP variant. The extension also exposes a logging `debug` switch. Each variant entry exposes these scalar dimensions: `packageBase`, `packageCount`, `activityCountPerPackage`, `excludeActivityJavaFile`, `otherCountPerPackage`, `methodCountPerClass`, `resPrefix`, `drawableCount`, and `stringCount` ([extension and config source](https://github.com/qq549631030/AndroidJunkCode/blob/cfcd9eed0b8d5a938033a9268a20e58e059b3039/library/src/main/kotlin/cn/hx/plugin/junkcode/ext/JunkCodeConfig.kt#L13-L39), [variant selection](https://github.com/qq549631030/AndroidJunkCode/blob/cfcd9eed0b8d5a938033a9268a20e58e059b3039/library/src/main/kotlin/cn/hx/plugin/junkcode/plugin/AndroidJunkCodePlugin.kt#L24-L39)).

It also exposes callback hooks for package name, Activity plus layout, ordinary class name, method name/body, type body, drawable, string, resource keep XML, ProGuard text, and whole Java/resource/Manifest generation. These callbacks are public configuration but are annotated `@Internal`, so their effects are not modeled as Gradle inputs ([callback surface](https://github.com/qq549631030/AndroidJunkCode/blob/cfcd9eed0b8d5a938033a9268a20e58e059b3039/library/src/main/kotlin/cn/hx/plugin/junkcode/ext/JunkCodeConfig.kt#L41-L78), [worked configuration examples](https://github.com/qq549631030/AndroidJunkCode/blob/cfcd9eed0b8d5a938033a9268a20e58e059b3039/app/build.gradle.kts#L64-L227)).

## XmlClassGuard 1.2.7

### Facts: public configuration and task families

The extension has exactly five configuration dimensions: `findAndConstraintReferencedIds`, `findAabConstraintReferencedIds`, `mappingFile`, `packageChange`, and `moveDir` ([extension source](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/entensions/GuardExtension.kt#L10-L29)). The plugin creates separate variant tasks for class guarding, Manifest package change, directory movement, and optional ConstraintLayout-ID discovery; the README explicitly says these task families are independent ([task registration](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/XmlClassGuardPlugin.kt#L50-L80), [task overview](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/README.md#L111-L128)).

### Facts: exact `xmlClassGuard` discovery surface

The class-guard task scans the application project plus local Android project dependencies reached through `api`/`implementation` (recursive dependency traversal continues through `api`). It does not scan external AAR/JAR source or bytecode. For each project it uses `main` plus matching variant source sets, but the Manifest helper selects only the `main` Manifest ([project traversal and source-set helpers](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/utils/ProjectExt.kt#L42-L149), [task project list](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/utils/TaskExt.kt#L11-L18)).

| Input surface | Class references recognized |
|---|---|
| `AndroidManifest.xml` | `application@android:name`, and direct application children named `activity`, `service`, `receiver`, or `provider`, using `android:name`. `activity-alias`, instrumentation, and other nodes are not selected ([Manifest parser](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/utils/ProjectExt.kt#L194-L216)). |
| `res/navigation*/*.xml` | Direct root-child `<fragment android:name="…">` nodes. When Safe Args is applied and the fragment node has children, the corresponding generated `*Directions` name is also mapped ([navigation parser](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/utils/ProjectExt.kt#L180-L191), [Directions handling](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/tasks/XmlClassGuardTask.kt#L43-L60)). |
| `res/layout*/*.xml` and `res/xml*/*.xml` | Every node's `tools:context`, `app:layout_behavior`, `app:layoutManager`, and `android:name`; non-whitelisted element names (custom views); and Data Binding `<variable type>` / `<import type>` values. The hard-coded element whitelist contains common framework/AndroidX/Material view tags and structural tags ([layout/XML parser and whitelist](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/utils/ProjectExt.kt#L18-L29), [parser](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/utils/ProjectExt.kt#L152-L177)). |

A discovered string is acted on only when a matching package directory exists in the application or one of those local Android project dependencies. Relative names beginning with `.` are expanded against that project's namespace/package ([guard filtering and replacement](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/tasks/XmlClassGuardTask.kt#L63-L119)).

### Facts: exact mutation surface and adjacent features

`xmlClassGuard` is a source-tree rewrite, not bytecode obfuscation. It renames/moves direct `.java`/`.kt` files in each mapped directory, rewrites package/class references as text across Java/Kotlin files, updates the selected XML/Manifest files, handles Kotlin top-level/JVM-name associations, and writes directory/class mappings. A manually seeded directory mapping can therefore include otherwise undiscovered classes, but only direct Java/Kotlin files in that directory, not its subdirectories ([file renaming and Kotlin associations](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/model/Mapping.kt#L42-L121), [source reference rewrite](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/tasks/XmlClassGuardTask.kt#L123-L177), [manual mapping contract](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/README.md#L197-L213)). It does not update `proguard-rules.pro`; upstream explicitly requires that to be repaired manually ([upstream warning](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/README.md#L259-L267)).

The separate `packageChange` task changes the Manifest `package`, Gradle `namespace`, relative Manifest class names, layout `tools:context`/`app:layoutManager`, and Java/Kotlin references to `R`, `BR`, `BuildConfig`, and `databinding`; it does not change `applicationId` ([package-change implementation](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/tasks/PackageChangeTask.kt#L31-L97), [documented boundary](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/README.md#L157-L169)). The separate `moveDir` task rewrites Manifest, layout/navigation/XML, AIDL, Java, and Kotlin text and physically moves matching Java/Kotlin/AIDL directory trees ([move implementation](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/tasks/MoveDirTask.kt#L32-L119)).

Optional ConstraintLayout discovery scans layout XML in all Android subprojects, reads `app:constraint_referenced_ids`, and adds `*.R.id.<id>` entries to AabResGuard's whitelist (or `R.id.<id>` for AndResGuard) ([ID discovery](https://github.com/liujingxing/XmlClassGuard/blob/0c36e1dc7dcfa2acdaf5ad2982341f50438cebb9/plugin/src/main/java/com/xml/guard/tasks/FindConstraintReferencedIdsTask.kt#L32-L80)).

## AabResGuard at `e8f3a5d…`

### Facts: public Gradle dimensions and operation order

The Gradle extension exposes `enableObfuscate` (default `true`), incremental `mappingFile`, resource `whiteList`, `obfuscatedBundleFileName`, `mergeDuplicatedRes`, `enableFilterFiles` plus `filterList`, and `enableFilterStrings` plus `unusedStringPath` and `languageWhiteList` ([extension source](https://github.com/bytedance/AabResGuard/blob/e8f3a5d361ce61a3d4fa8bafb9d030bbe459c400/plugin/src/main/kotlin/com/bytedance/android/plugin/extensions/AabResGuardExtension.kt#L9-L33)). The combined command executes in this order: file filtering, string/language filtering, duplicate-resource merge, resource obfuscation, bundle serialization, then signing ([command pipeline](https://github.com/bytedance/AabResGuard/blob/e8f3a5d361ce61a3d4fa8bafb9d030bbe459c400/core/src/main/java/com/bytedance/android/aabresguard/commands/ObfuscateBundleCommand.java#L172-L232)).

| Resource-directory and file-path obfuscation | Maps resource directories to short `res/<name>` paths, renames file-backed `res/` entries while preserving their suffix (including `.9.png`), and rewrites ResourceTable file references to the new path. | Incremental obfuscation | Reads prior directory, resource-name, and entry-path mappings, reserves already-used short names, reuses applicable mappings, and emits `resources-mapping.txt` with all three mapping sections ([mapping reuse](https://github.com/bytedance/AabResGuard/blob/e8f3a5d361ce61a3d4fa8bafb9d030bbe459c400/core/src/main/java/com/bytedance/android/aabresguard/executors/ResourcesObfuscator.java#L64-L76), [reserved-name reconstruction](https://github.com/bytedance/AabResGuard/blob/e8f3a5d361ce61a3d4fa8bafb9d030bbe459c400/core/src/main/java/com/bytedance/android/aabresguard/executors/ResourcesObfuscator.java#L120-L140), [mapping parser](https://github.com/bytedance/AabResGuard/blob/e8f3a5d361ce61a3d4fa8bafb9d030bbe459c400/core/src/main/java/com/bytedance/android/aabresguard/parser/ResourcesMappingParser.java#L18-L74)). |

No separate compression-mode/level, image recompression, WebP conversion, XML minification, resource-ID compaction, or unused non-string resource removal option exists in this extension or command. Repackaging delegates to bundletool's `AppBundleSerializer`; therefore “optimization” at this revision means the explicit duplicate merge and filters above, not a general compression contract ([packager](https://github.com/bytedance/AabResGuard/blob/e8f3a5d361ce61a3d4fa8bafb9d030bbe459c400/core/src/main/java/com/bytedance/android/aabresguard/bundle/AppBundlePackager.java#L17-L35)).

### Facts: keep and exclusion controls

- `whiteList` is a set of glob-like rules: `.`, `?`, `*`, and `+` are converted to regex equivalents and the entire value must match. The same matcher is called for ResourceTable full names such as `*.R.string.name` and bundle resource paths such as `base/res/drawable/icon.png`; Android-system names beginning `android:` are unconditionally kept ([pattern conversion](https://github.com/bytedance/AabResGuard/blob/e8f3a5d361ce61a3d4fa8bafb9d030bbe459c400/core/src/main/java/com/bytedance/android/aabresguard/utils/Utils.java#L34-L50), [keep check](https://github.com/bytedance/AabResGuard/blob/e8f3a5d361ce61a3d4fa8bafb9d030bbe459c400/core/src/main/java/com/bytedance/android/aabresguard/executors/ResourcesObfuscator.java#L353-L364), [first-party Google-services examples](https://github.com/bytedance/AabResGuard/blob/e8f3a5d361ce61a3d4fa8bafb9d030bbe459c400/wiki/en/WHITELIST.md#L1-L16)).
- `mappingFile` is reuse, not a keep rule: an existing mapping remains eligible only while the resource is not newly matched by the whitelist; a whitelist match removes that resource's old name mapping ([mapping/whitelist interaction](https://github.com/bytedance/AabResGuard/blob/e8f3a5d361ce61a3d4fa8bafb9d030bbe459c400/core/src/main/java/com/bytedance/android/aabresguard/executors/ResourcesObfuscator.java#L166-L200)).
- `languageWhiteList` keeps locale variants during the destructive string-language filter; it does not prevent the string resource entry name from being obfuscated later. `filterList` selects files to delete and is likewise not a resource-name keep mechanism ([operation order](https://github.com/bytedance/AabResGuard/blob/e8f3a5d361ce61a3d4fa8bafb9d030bbe459c400/core/src/main/java/com/bytedance/android/aabresguard/commands/ObfuscateBundleCommand.java#L175-L219)).

## Kaleido inference (not upstream fact)

1. **AndroidJunkCode-equivalent parity should name two levels.** A faithful default contract is Java Activity + ordinary-class generation, layouts, XML drawables, strings, application-child Activity declarations, and retention rules. Broader source/resource/component/Manifest support would be a Kaleido extension, not “exact 2.0.0 default parity.” Arbitrary executable callbacks also conflict with Kaleido's deterministic, declarative input contract and should not be copied into the public DSL.
2. **XmlClassGuard-equivalent parity should be defined by reference surfaces, not by its destructive implementation.** The upstream behavioral floor is the listed Manifest, navigation, layout/XML, Data Binding, Java/Kotlin, local-project-module, mapping, and escape-hatch surface. Claiming external binary dependency renaming, all XML attributes, `activity-alias`, reflection, JNI, generated frameworks beyond Safe Args, or ProGuard synchronization would exceed 1.2.7 and needs an explicit Kaleido contract plus tests.
3. **AABResGuard-equivalent “obfuscation and optimization” has a bounded upstream meaning.** Entry-name, resource-directory, and file-path obfuscation plus incremental mapping are the obfuscation core; same-module duplicate-file merge, restricted file deletion, and string/language filtering are the available optimization operations. A compression strategy, generic resource shrinking, or image optimization is new product scope rather than parity.
4. **Keep semantics need separate Kaleido concepts.** Resource-name/path keep rules, dynamic-lookup/framework exemptions, language retention, deletion filters, and prior mapping reuse have different effects upstream and should not be collapsed into one ambiguous whitelist.

## Remaining unknowns

- This source audit does not establish which upstream edge cases produce a valid installable artifact; that requires fixture builds and runtime acceptance tests.
- AndroidJunkCode's whole-tree callbacks make the theoretical output type open-ended, but the upstream API does not enumerate or validate supported custom Java/resource/Manifest schemas.
- XmlClassGuard's text replacement can encounter reflection, JNI, annotation-processor output, generated sources, aliases, or XML forms outside the parser above; upstream documents no complete compatibility matrix.
- AabResGuard does not document a formal dynamic-resource-lookup detector. The shipped whitelist examples are manual rules, so a complete automatic keep set is not established by this revision.
