# Define the keep and escape-hatch model

Type: grilling
Status: resolved
Blocked by: 05

## Question

For the now-defined class, Manifest/XML, R8, generated-code, and final-AAB resource surfaces, which reflection, JNI, annotation/generated-framework, dynamic resource lookup, public-resource, and third-party SDK patterns are detected automatically, which require declarative Consumer Project keeps, which safely preserve the original name or path, and which fail the Release build because Kaleido cannot prove reference integrity?

## Answer

Kaleido models preservation as an additive set of typed Protection Requirements, not one keep boolean. A requirement independently protects reachability, original class/member identity, descriptor types, required runtime attributes, a resource entry name, or a packaged path. Application rules, dependency consumer rules, Kaleido inference, Android resource declarations, and explicit Consumer Project declarations contribute to the union; no source may silently weaken another source's protection.

Automatic handling is limited to finite, closed targets:

- Direct bytecode, class-literal, Manifest, XML, compiled resource-ID, and binary-XML edges participate in coordinated transformation rather than forcing their targets to retain original identities.
- Exact string-reflection targets retain the minimum necessary reachability, class/member names, descriptor closure, and runtime attributes instead of relying on general string rewriting.
- Managed `native` declarations and cross-validated exact JNI symbol, registration, class, method, or field lookups retain the required managed names and descriptors. `RegisterNatives` is not a rename exemption. A native library or `System.loadLibrary` signal alone is reported but does not fail.
- `tools:keep`, exact `Resources.getIdentifier()` targets, and public resources retain existence and original entry names. A packaged path is retained only when a confirmed path-based lookup requires it; ordinary compiled ID/table references may still use transformed entry names and paths.
- KAPT/KSP and other generated frameworks are judged from their final compiled outputs. Direct generated bytecode edges are transformed normally; resolved consumer rules remain R8 inputs with provenance and are translated into pre-R8 Protection Requirements where they constrain a target Kaleido could otherwise rename. Framework-specific automatic handling requires a minified Release fixture, not only a processor coordinate or annotation name.

Runtime-computed reflection/JNI/resource/member/path names, generated-name conventions, and other open-ended couplings require a bounded Escape Hatch. Each declaration names its protection dimensions, an exact target or bounded package/resource-prefix pattern, and a reason; Kaleido resolves and reports its target count. Broad bounded patterns warn, while a global bypass is invalid. A zero-match declaration, a conflict such as `tools:discard` against required protection, or a confirmed coupling that remains unclosed fails the Release build.

Dependency classes are analyzed but not renamed by Kaleido. Dependency consumer rules remain additive, and dependency-owned resource entry names and packaged paths are preserved by default in the MVP because Kaleido does not rewrite dependency code. Static scanning reports its declared scope and discovered signals; it never claims to prove the absence of reflection, JNI, dynamic resource lookup, or equivalent runtime behavior.

Safe Profile and Full Profile use the same protection and fail-closed rules. Full Profile controls cannot override dynamic-reference, public-resource, SDK, or packaged-path protection. Direct Application-module external code loading, hotfix, and pluginization remain unsupported topology and cannot be enabled through an Escape Hatch.
