# Define the upgrade, deprecation, and migration policy

Type: grilling
Status: resolved
Blocked by: 04, 06, 08, 09

## Question

Across Kaleido and supported AGP releases, what compatibility window, semantic-versioning rules, DSL and intermediate-schema deprecation period, mapping/report migration guarantees, upgrade diagnostics, and documented Consumer Project migration path keep existing Release Evidence Sets usable without promising indefinite compatibility?

## Comments

- Research evidence: [`upgrade-deprecation-migration-evidence.md`](../research/upgrade-deprecation-migration-evidence.md) establishes from current Gradle, Android, R8, SemVer, JSON Schema, and IETF primary sources that no external N-1 window applies automatically; compatibility must be an exact tested matrix, public deprecation and breaking changes follow SemVer, mappings are release-specific evidence, external evidence schemas and internal cache schemas need separate lifecycles, and upgrade-time cache misses are expected rather than migrated.
- Decision round 1: each Kaleido release publishes an immutable Compatibility Matrix of exact Kaleido, AGP patch, Gradle, runtime JDK, Build Tools, compileSdk, and Kotlin-mode combinations. The MVP targets every AGP `9.0.1`–`9.3.2` candidate row but publishes the proven subset if any row fails its complete Release fixture; it never claims generic AGP 9, preview, or untested support. Adding a proven row is minor-compatible and removing one is a breaking major change.
- Decision round 1: Kaleido `1.0.0` defines the plugin ID, DSL types/properties/enums and Provider semantics, defaults and validation/failure behavior, Profiles, Compatibility Matrix, diagnostic machine identity, Artifact Report schema, Release Evidence Set membership/identity, and Kaleido mapping envelopes/binding semantics as its public Interface. A compatible fix is patch; additive DSL/toolchain/schema/diagnostic support and deprecation are minor; removal/rename, changed existing defaults or meaning, support shrinkage, diagnostic-identity change, or broken report/mapping reading are major. Cross-version output-byte or mapping equality is not promised when public semantics remain compatible.
- Decision round 1: internal task names/graph, engine types, Adoption Plan, rewrite plans, receipts, and cache formats remain implementation rather than public Interface. Their upgrade may produce an intentional cache miss without cache migration. Unsupported, preview, and removed toolchain combinations fail with stable `KLD-COMPAT-*` diagnostics before task registration, secret resolution, or artifact mutation; diagnostics include detected versions, the exact supported combinations, and an actionable upgrade/downgrade route. There is no force override, and only a still-supported combination with a scheduled removal may warn.
- Decision round 2: public DSL, diagnostic fields, and external schema members are deprecated only in a minor while retaining their existing semantics. Removal requires the next major, at least one intervening non-preview minor, and at least 90 days; if necessary Kaleido publishes a Bridge Release. One canonical `KLD-DEPRECATION-*` warning identifies the old declaration path, replacement, first deprecated version, and removal major. A removed form fails with a mechanical migration example rather than being ignored.
- Decision round 2: every Artifact Report declares a schema family, independent `major.minor`, immutable schema URI, and JSON Schema dialect. Minor evolution is backward-readable addition only; every reader in a Kaleido major reads all report minors emitted by that major, and the next Kaleido major reads at least its current and immediately previous report schema major. Forward-reading by old readers and indefinite latest-binary support are not promised. Historical Release Evidence Sets remain byte-immutable; a future converter may create only a provenance-bound derived view, never replace the source set.
- Decision round 2: every Release Evidence Set retains its exact raw Kaleido class, original AGP/R8, retrace-compatible composed, and resource mappings together with R8/compiler and mapping versions, `pg_map_id`, `pg_map_hash`, full mapping digests, composition version/input digests, and the validated retrace tool coordinates/version. Kaleido promises neither cross-release obfuscated-name stability nor implicit historical-mapping input. Historical usability means the matching published mapping and recorded tool can retrace that exact artifact, not that the latest retrace remains indefinitely compatible.
- Decision round 2: Adoption Plan, stage plans, receipts, and other hidden intermediate schemas receive explicit schema/policy/producer versions as task inputs but no public deprecation window or cache migration Interface. Plugin/schema upgrades intentionally miss incompatible cache entries; a pipeline may not mix producer/schema majors, and unknown or stale formats fail closed. Any format later exposed as a documented evidence or reader Interface becomes subject to the public deprecation and reader-window policy.
- Decision round 3: every breaking migration first validates and archives the current Release Evidence Set, selects an exact target Compatibility Matrix row, upgrades to the latest Bridge Release, removes all deprecations while retaining a publishable baseline, then changes AGP, Gradle Wrapper, JDK/SDK, and target Kaleido major one dimension at a time. A clean target build expects old-cache misses and must validate new evidence closure, matching-mapping retrace, Bundle/signing, and all reproducibility gates while retaining the old set. If no single Bridge Release spans both ends, documentation supplies an explicit multi-hop route.
- Decision round 3: machine upgrade diagnostics are partitioned as `KLD-COMPAT-*` for unsupported toolchains, `KLD-DEPRECATION-*` for still-supported scheduled removal, `KLD-SCHEMA-*` for unreadable/stale/mixed schema, and `KLD-MIGRATION-*` for a required bridge, matching mapping, or migration step. Every release publishes its immutable Compatibility Matrix, SemVer classification, schema versions, deprecation/removal inventory, Bridge Release route, and executable migration examples; ordinary update availability is not a warning.
- Decision round 3: release-blocking tests run a complete Release fixture for every supported matrix row and stable failure fixtures for adjacent unsupported/preview rows; prove deprecated/replacement Adoption Plan equivalence and one sanitized warning; read every same-major report minor and the previous report major; preserve and retrace R8 mapping metadata with a real obfuscated stack; prove affected-task cache misses without stale-schema restoration or unrelated-variant invalidation; and independently pass the four reproducibility gates before and after upgrade without requiring cross-version byte equality.
- Decision round 3: only a confirmed security risk, legal/licensing requirement, or upstream removal that makes safe/correct support impossible may waive the 90-day or Bridge Release minimum. The break still requires a new Kaleido major and a published advisory with affected versions, rationale, and executable migration route; no patch/minor may hide it. An old plugin may be marked unsupported, but published binaries and historical Release Evidence Sets remain immutable and cannot be rewritten or represented as new evidence.

## Answer

Every Kaleido release publishes an immutable Compatibility Matrix of exact Kaleido, AGP patch, Gradle, runtime JDK, Build Tools, compileSdk, and Kotlin-mode combinations proven by complete Release fixtures. The MVP targets all candidate AGP `9.0.1`–`9.3.2` rows but publishes only the proven subset; previews, untested combinations, and a generic “AGP 9” claim are unsupported. Adding a proven row is minor-compatible, while removing one is a major break.

Kaleido `1.0.0` applies SemVer to the Adoption Contract, defaults and failure semantics, Profiles, Compatibility Matrix, diagnostic machine identity, Artifact Report schema, Release Evidence Set membership/identity, and public mapping envelopes. Compatible fixes are patch releases; additive declarations, supported combinations, schema fields, diagnostics, and deprecations are minor releases; removal/rename, changed existing meaning/defaults, support shrinkage, diagnostic-identity changes, and broken report/mapping reading require a major. Cross-version output-byte and obfuscated-name equality are not public guarantees.

Public DSL, diagnostic fields, and external schema members retain their semantics when deprecated in a minor, remain through at least one subsequent non-preview minor and 90 days, and may be removed only in a later major. A Bridge Release spans the old and target contracts so Consumer Projects can clear stable `KLD-DEPRECATION-*` warnings before changing toolchains. Unsupported combinations fail before task registration, secret resolution, or artifact mutation through `KLD-COMPAT-*`; `KLD-SCHEMA-*` and `KLD-MIGRATION-*` cover unreadable/mixed formats and required migration steps. No force override or ordinary update-available warning exists.

Artifact Report schemas use an independent family, `major.minor`, immutable URI, and JSON Schema dialect. A Kaleido major reads all report minors it emits, and the next major reads at least the immediately previous report major; older evidence remains interpretable through its immutable schema, recorded toolchain, matching mappings, and archived tools rather than an indefinite latest-binary promise. Release Evidence Sets are never rewritten in place, and any future migration creates only a provenance-bound derived view.

Each release retains the exact raw Kaleido, original AGP/R8, retrace-compatible composed, and resource mappings, including R8/compiler and mapping versions, map ID/hash, full digests, composition provenance, and validated retrace-tool coordinates. Kaleido neither stabilizes names across releases nor consumes historical mappings implicitly. Hidden Adoption Plan, stage plan, receipt, task, and cache schemas have explicit producer/policy versions but no public deprecation window; incompatible upgrades intentionally miss cache entries and reject mixed or stale outputs.

A breaking Consumer Project migration archives and validates the old Release Evidence Set, selects an exact target matrix row, enters the latest Bridge Release, removes deprecations, then changes AGP, Gradle Wrapper, JDK/SDK, and target Kaleido major one dimension at a time before independently validating the new evidence, retrace, signing, Bundle, cache, and reproducibility gates. Only a confirmed security risk, legal/licensing requirement, or upstream removal that makes safe support impossible may shorten the bridge period; the break still requires a major, advisory, and executable route. See [`ADR-0010`](../../../docs/adr/0010-version-public-contracts-with-finite-migration-windows.md) and the [`research evidence`](../research/upgrade-deprecation-migration-evidence.md).
